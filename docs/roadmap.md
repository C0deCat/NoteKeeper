# Roadmap

## Общая суть проекта

NoteKeeper - приложение для преобразования длинных аудиозаписей настольных ролевых игр в удобные текстовые материалы по сессии.

На вход ожидается одна аудиозапись типичной длительностью от 3 до 5 часов. Все участники записаны на одной общей дорожке, без разделения по отдельным аудиоканалам. Поэтому пайплайн должен выполнять не только speech recognition, но и диаризацию говорящих.

Основной результат работы пайплайна:

- транскрипт в Markdown формате;
- рекап транскрипта в Markdown формате, сгенерированный с помощью LLM.

## Основной пайплайн

1. Принять одну аудиозапись на вход.
2. Подготовить и нормализовать аудио для обработки.
3. Выполнить speech recognition.
4. Выполнить диаризацию говорящих.
5. Сформировать транскрипт, где лейблы говорящих сопоставлены с конкретными именами участников.
6. Сгенерировать краткое содержание сессии на основе транскрипта.
7. Сохранить метаданные джобы и другие необходимые данные выполнения.
8. Вернуть транскрипт и рекап как Markdown файлы.

## Предположения о входных данных

- Один входной файл соответствует одной сессии настольной ролевой игры.
- Все говорящие записаны на одной общей аудиодорожке.
- Типичная длительность записи: от 3 до 5 часов.
- Если сопоставление известно, в финальном транскрипте должны использоваться имена участников, а не технические speaker labels.

## Предположения о выходных данных

- Транскрипты возвращаются в Markdown.
- Рекапы возвращаются в Markdown.
- Пайплайн должен сохранять достаточно метаданных, чтобы понимать, когда и как была выполнена конкретная джоба.

## Предварительный стек

### Уже есть в проекте

- Python
- Typer: основа для CLI-интерфейса.

### Ключевые инструменты и библиотеки

- ffmpeg: подготовка аудио, probing, конвертация, извлечение дорожек, нормализация.
- WhisperX: speech recognition, alignment и workflow вокруг транскрипции с диаризацией.
- SpeechBrain: speaker embeddings и embedding-based speaker identification для автоматического сопоставления говорящих.
- ECAPA-TDNN: модель speaker recognition внутри SpeechBrain для построения embeddings по voice samples и фрагментам речи.
- Pydantic: модели данных и валидация для джоб, кампаний, участников, voice samples, сегментов транскрипта, speaker mappings, конфигурации пайплайна и ответов LLM/API.
- SQLite: локальное хранение метаданных выполненных джоб и других необходимых данных приложения.
- DeepSeek API: основной LLM-инструмент для генерации рекапов.
- FastAPI: Web API слой поверх пайплайна, кампаний, джоб и результатов.
- React: Web UI для локального и удаленного доступа к приложению.

Pydantic нужен, потому что проект будет передавать структурированные данные между несколькими стадиями: подготовкой аудио, транскрипцией, диаризацией, сопоставлением говорящих с именами, генерацией рекапа и сохранением метаданных. Явные модели помогут удержать границы между стадиями понятными и снизить риск ошибок при развитии форматов данных.

## Roadmap

Реализация проекта будет разбита на несколько стадий. На каждой стадии проект должен оставаться полностью функциональным работающим продуктом с законченным end-to-end flow.

### Стадия 1: Campaign-Based Pipeline

Первая стадия должна позволять обработать запись игровой сессии в контексте заранее заведенной кампании и получить два финальных артефакта: транскрипт с именованными говорящими и рекап.

#### Campaign

В программе можно создать сущность campaign.

Campaign хранит:

- список присоединенных к ней участников;
- voice samples участников;
- метаданные, необходимые для обработки новых записей в рамках этой кампании.

#### Участники и voice samples

Для каждого участника campaign можно добавить voice sample: короткую запись голоса, типично длиной от 10 до 15 секунд.

Каждый voice sample должен иметь метаданные:

- какому участнику он принадлежит;
- какая у него длительность;
- к какой campaign он относится;
- где хранится соответствующий аудиофайл.

Эти voice samples используются как известные аудиофрагменты, по которым можно сопоставить анонимные speaker labels с конкретными игроками.

#### Обработка новой записи

К campaign можно присоединить новую аудиозапись игровой сессии. При обработке этой записи пайплайн выполняет следующие шаги:

1. Берет исходную аудиозапись сессии.
2. Добавляет к ней voice samples всех участников campaign.
3. Выполняет транскрипцию и диаризацию полученного аудио.
4. Получает транскрипт с анонимными speaker labels.
5. По известным метаданным voice samples определяет, какой анонимный speaker label соответствует какому участнику.
6. Автоматически заменяет анонимные speaker labels на именованные speaker labels.
7. Формирует Markdown транскрипт с именами участников.

Такой подход позволяет использовать заранее известные голосовые примеры как опорные фрагменты для автоматического разрешения speaker labels после диаризации.

#### Обработка сбоев ASR и диаризации

Если в процессе ASR или диаризации обнаружены проблемы, приложение должно выдавать предупреждение и давать возможность вручную исправить сопоставление говорящих.

Примеры проблем:

- обнаружено больше speaker labels, чем ожидается по участникам campaign;
- обнаружено меньше speaker labels, чем ожидается;
- voice sample не удалось надежно сопоставить с анонимным speaker label;
- несколько участников выглядят сопоставленными с одним и тем же speaker label;
- часть транскрипта осталась с техническими speaker labels.

В таких случаях пользователь должен иметь возможность вручную переназначить или доназначить говорящих перед генерацией финального транскрипта и рекапа.

#### Генерация рекапа

После получения транскрипта с именами участников он передается на обработку большой языковой модели через DeepSeek API.

Так как транскрипт ожидается большим, обработка должна выполняться чанками. Ориентировочный размер чанка: 25-35 тысяч токенов.

Пайплайн генерации рекапа:

1. Разбить транскрипт на крупные последовательные фрагменты по 25-35 тысяч токенов.
2. Для каждого фрагмента сгенерировать отдельный частичный рекап.
3. Сохранить связь каждого частичного рекапа с временным участком или диапазоном исходного транскрипта.
4. Собрать частичные рекапы в единый Markdown рекап сессии.
5. При необходимости сгенерировать итоговое summary по всем частичным рекапам.
6. Добавить итоговое summary в конец рекапа.

Итоговое summary должно фиксировать наиболее важные события, решения, открытия, незавершенные вопросы и другие ключевые вещи по сессии.

#### Результат первой стадии

К концу первой стадии приложение должно поддерживать полный flow:

1. Создать campaign.
2. Добавить участников campaign.
3. Добавить voice samples участников.
4. Присоединить к campaign новую аудиозапись игровой сессии.
5. Получить транскрипт с именованными говорящими.
6. При необходимости вручную исправить speaker mappings.
7. Получить Markdown рекап, собранный из частичных рекапов и итогового summary.
8. Сохранить метаданные выполненной джобы в SQLite.

### Стадия 2: SpeechBrain Speaker Identification

Вторая стадия должна заменить полуавтоматическое сопоставление говорящих на более надежный автоматический pipeline на основе speaker embeddings.

Ключевая идея стадии: использовать SpeechBrain с ECAPA-TDNN для построения embeddings по заранее сохраненным voice samples участников campaign и по speech turns новой записи. Эти embeddings используются для автоматического сопоставления говорящих с участниками campaign. WhisperX при этом остается основной частью ASR/alignment flow и используется для финального назначения speaker labels словам и сегментам транскрипта.

#### Роль WhisperX

WhisperX отвечает за:

- speech recognition;
- alignment и word-level timestamps;
- представление транскрипта в виде сегментов и слов с временными метками;
- финальное назначение speaker labels словам и сегментам на основании diarization intervals.

На этой стадии WhisperX не должен быть единственным источником имен говорящих. Его задача - дать качественный транскрипт и временную структуру, к которой можно применить результат speaker identification.

#### Роль SpeechBrain и ECAPA-TDNN

SpeechBrain используется как embedding-based speaker identification слой.

При добавлении voice sample участника:

1. Voice sample приводится к ожидаемому аудиоформату, например 16 kHz mono.
2. SpeechBrain ECAPA-TDNN преобразует voice sample в speaker embedding.
3. Embedding сохраняется вместе с метаданными sample и участника.

При обработке новой записи:

1. Аудио разбивается на speech turns или другие speaker-bearing фрагменты.
2. Для каждого speech turn строится embedding через SpeechBrain ECAPA-TDNN.
3. Embedding speech turn сравнивается с enrollment embeddings участников campaign.
4. Если сходство выше выбранного threshold, speech turn автоматически сопоставляется с конкретным участником.
5. Если уверенности недостаточно, фрагмент помечается как требующий проверки.

Такой подход разделяет две задачи:

- diarization: определить, кто и когда говорит, пусть даже с техническими speaker labels или speech turns;
- identification: сопоставить найденные speech turns или speaker clusters с конкретными участниками campaign.

#### Интеграция SpeechBrain с WhisperX

Интеграция должна происходить через промежуточное представление speaker intervals.

Ожидаемый flow:

1. WhisperX выполняет ASR и alignment исходной записи.
2. Pipeline получает word-level timestamps и сегменты транскрипта.
3. SpeechBrain-based компонент обрабатывает аудио и формирует speaker turns.
4. Для speaker turns строятся embeddings.
5. Embeddings сравниваются с сохраненными embeddings участников campaign.
6. Speaker turns получают именованные labels участников там, где confidence достаточно высокий.
7. Результат приводится к WhisperX-compatible diarization intervals: `start`, `end`, `speaker`.
8. WhisperX-compatible assignment назначает speaker labels словам и сегментам транскрипта.
9. На выходе формируется Markdown транскрипт с именованными говорящими.

В результате SpeechBrain не заменяет WhisperX целиком. Он дополняет pipeline слоем speaker identification, а WhisperX продолжает отвечать за ASR, alignment и применение speaker intervals к транскрипту.

#### Хранение embeddings и метаданных

Для каждого voice sample нужно сохранять:

- ссылку на участника;
- ссылку на campaign;
- путь к исходному sample;
- длительность sample;
- параметры аудиоподготовки;
- используемую модель SpeechBrain;
- версию или идентификатор модели;
- полученный speaker embedding;
- дату создания embedding.

Для обработанной записи полезно сохранять:

- найденные speech turns;
- confidence сопоставления speech turns с участниками;
- threshold, использованный при сопоставлении;
- фрагменты, требующие ручной проверки;
- финальные speaker intervals, примененные к транскрипту.

#### Обработка неопределенности

Даже на второй стадии pipeline должен сохранять возможность ручной проверки и исправления.

Примеры ситуаций:

- speech turn не удалось уверенно сопоставить ни с одним участником;
- несколько участников имеют близкое значение similarity;
- найден speaker, которого нет среди участников campaign;
- качество voice sample недостаточно для надежного embedding;
- качество записи сессии слишком низкое для уверенного speaker identification.

В этих случаях приложение должно выдавать предупреждение и позволять вручную исправить mapping перед генерацией финального транскрипта и рекапа.

#### Результат второй стадии

К концу второй стадии приложение должно поддерживать более автоматический flow:

1. Создать campaign.
2. Добавить участников campaign.
3. Добавить voice samples участников.
4. Автоматически построить и сохранить speaker embeddings для voice samples.
5. Присоединить к campaign новую аудиозапись игровой сессии.
6. Выполнить ASR и alignment через WhisperX.
7. Выполнить speaker identification через SpeechBrain ECAPA-TDNN по speech turns.
8. Автоматически получить transcript speaker intervals с именами участников.
9. Сформировать Markdown транскрипт с именованными говорящими.
10. При необходимости вручную проверить и исправить неопределенные speaker mappings.
11. Сгенерировать Markdown рекап через DeepSeek API по chunk-based flow.
12. Сохранить метаданные выполненной джобы, embeddings, confidence и speaker intervals в SQLite.

### Стадия 3: Web API и Web UI

К началу третьей стадии в проекте уже должен существовать готовый сервис для транскрипции, speaker identification, генерации рекапов и хранения метаданных. Задача третьей стадии - предоставить к этому сервису удобный программный и пользовательский доступ через Web API и Web UI.

#### API слой

Для Web API используется FastAPI.

API должен открыть доступ к основным сущностям и операциям приложения:

- управление campaigns;
- управление участниками campaign;
- загрузка и управление voice samples;
- запуск обработки новой аудиозаписи;
- получение статуса джобы;
- получение предупреждений и неопределенных speaker mappings;
- ручное исправление speaker mappings при необходимости;
- получение Markdown транскрипта;
- получение Markdown рекапа;
- доступ к метаданным выполненных джоб.

API должен работать как локально, так и в развернутом окружении. Локальный запуск нужен для персонального использования на машине пользователя, а развернутый режим - для доступа к приложению через домен и интернет.

#### Web UI

Для Web UI используется React.

Web UI должен позволять пользователю выполнять основной flow без прямой работы с CLI:

1. Создавать и просматривать campaigns.
2. Добавлять участников campaign.
3. Загружать voice samples для участников.
4. Загружать новую аудиозапись игровой сессии.
5. Запускать обработку записи.
6. Отслеживать статус выполнения джобы.
7. Просматривать предупреждения pipeline.
8. Исправлять speaker mappings, если автоматическое сопоставление требует проверки.
9. Просматривать и скачивать Markdown транскрипт.
10. Просматривать и скачивать Markdown рекап.
11. Просматривать метаданные выполненных джоб.

Web UI должен поддерживать два режима использования:

- локальный запуск вместе с локальным API;
- развертывание на домене с доступом через интернет.

#### Разделение ответственности

На третьей стадии важно сохранить pipeline как самостоятельный application service, доступный из разных интерфейсов.

Ожидаемое разделение:

- core pipeline: транскрипция, diarization, speaker identification, recap generation;
- persistence layer: SQLite и хранение файловых артефактов;
- API layer: FastAPI endpoint'ы и схемы запросов/ответов;
- Web UI: React-приложение для пользовательского управления;
- CLI: может сохраниться как локальный интерфейс поверх тех же application services.

Такое разделение позволит использовать одну и ту же бизнес-логику из CLI, Web API и Web UI.

#### Результат третьей стадии

К концу третьей стадии приложение должно поддерживать:

1. Полный pipeline второй стадии через Web API.
2. Web UI для управления campaigns, участниками, samples, джобами, транскриптами и рекапами.
3. Локальный запуск API и Web UI.
4. Возможность развернуть Web UI на домене и сделать приложение доступным через интернет.
5. Возможность использовать API отдельно от Web UI.
6. Сохранение CLI как дополнительного интерфейса, если это не усложняет поддержку.
